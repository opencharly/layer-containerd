### 1. The service was never enabled

`service:` declares the same `containerd` name twice, because the init systems need different forms: `exec:` for supervisord in a pod, `use_packaged:` for systemd in a VM. **The packaged form had no `enable:` field — and `enable:` defaults to false.**

Measured on a real VM, via `layer-fireactions#1`'s bed: the unit read

```
○ containerd.service - containerd container runtime
     Loaded: loaded (/usr/lib/systemd/system/containerd.service; disabled; preset: dis…
```

**The distro ships containerd disabled**, so the substrate's own precondition step could not pass — even though the config it checks was correct: the `snapshotter = "native"` grep *above* that check succeeded, and only `systemctl is-active` failed.

The field is **`enable`**, not `enabled` — `spec/schema/boxmetadata.cue:55`. CUE's closed schema rejects the wrong spelling, which is why the name was read rather than recalled.

### 2. The bed asserted nothing

`check-containerd-vm` had **no `plan:` at all** — while its own `description:` claimed *"the plan asserts on the RUNNING guest that the declared snapshotter reports ok in `ctr plugins ls`"*. Its check phases logged `No plan steps defined for this image.`

**A bed that deploys, checks nothing and cleans up reports `PASS (steps=15)` and proves nothing** — the same vacuous-gate failure that has already cost three PRs in this leg their verdicts. The plan now declares the two assertions the description promised, and each reports its own failure on stderr.
