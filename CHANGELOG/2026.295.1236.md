# 2026.295.1236 — fix(containerd): pre-load xt_multiport for the CNI portmap plugin

## Summary

`opencharly/layer-containerd#5`: a rootless containerd lease cannot publish a port when the venue's
running kernel has no loadable `xt_multiport` — the CNI `portmap` plugin appends an
`iptables -m multiport` DNAT rule, and the append fails:

```
Warning: Extension multiport revision 0 not supported, missing kernel module?
iptables v1.8.13 (nf_tables): RULE_APPEND failed (No such file or directory)
```

This change makes the layer own the module's availability:

- one `run:` step loads `xt_multiport` at deploy time and persists it through
  `/etc/modules-load.d/charly-containerd.conf`, so a boot pre-loads it;
- the narrow package set the path needs is declared per distro — `iptables` (Arch) / `iptables-nft`
  (Fedora), the binary the CNI plugin execs, and `kmod` for `modprobe` — not a blanket netfilter set;
- a live venue whose running kernel has no module tree (a package upgrade replaced it — the issue's
  host state) now fails the deploy with a **"reboot this venue"** message instead of silently skipping
  the load and letting the port-publish fail later inside the CNI plugin;
- the repo's bed asserts the persistent declaration **and** performs the actual portmap append in a
  throwaway user + network namespace. The assertion lives in the bed's plan, not the candy plan, because
  the bed's member applies the candy while the bed's own plan is what `check-live` resolves and executes.

**Measured qualification, stated rather than hidden:** on a healthy kernel the module auto-loads on
first use, so the rule append alone does not distinguish the pre-fix venue. The persistent declaration
is the part this layer adds, and the bed fails without it.

The blockfile snapshotter stanza and the scratch-image preparation step are untouched (they arrived in
merged PR #4).
