# 2026.295.1933 — feat(containerd): own the version-4 host config, the generated seccomp profile, and the enabled services

## Summary

`opencharly/layer-containerd#7` — wave W4/C2. The layer still wrote a **version-2** containerd config on
the `native` snapshotter:

```
version = 2
[plugins."io.containerd.grpc.v1.cri".containerd]
  snapshotter = "native"
```

That shape cannot carry the host contract (`CONTAINERD-IMAGES.md` §1.1, `containerd-host`), and two of its
omissions are dangerous on a real host:

- **no gRPC address under `plugins."io.containerd.server.v1.grpc"`**. In a v4 config a top-level `[grpc]`
  is silently ignored and the daemon binds its default socket. MEASURED on containerd v2.4.2: a v4 file
  with `[grpc] address = "/tmp/bad.sock"` and no server-plugin block dumps with the server plugin address
  still `/run/containerd/containerd.sock`. A daemon started with such a file replaces a running host's
  system socket.
- **no `crun`/`krun` handlers, no narrow seccomp profile, buildkit never enabled.**

This change, in `candy/layer-containerd/charly.yml` and the repo's own bed:

- writes a **`version = 4`** `/etc/containerd/config.toml` with
  `imports = ["/etc/containerd/conf.d/*.toml"]`, the listener under
  `plugins."io.containerd.server.v1.grpc"` (`address = "/run/containerd/containerd.sock"`), the CRI
  snapshotter **`overlayfs`** (CONTAINERD.md §1 rule 3 / §3.3.2; `native` and the `blockfile` plugin stay
  served), `default_runtime_name = "crun"`, and `crun` + `krun` handlers — `krun` carrying
  `pod_annotations = ["krun.*"]` — both with `SystemdCgroup = true`;
- **generates** `/etc/containerd/seccomp/crabbox-userns.json` from the **installed** containerd's own
  `DefaultProfile()`: a small Go program (written by the candy) is built against the version
  `containerd --version` reports and appends `{"names":["unshare","clone"],"action":"SCMP_ACT_ALLOW"}`
  with **no `args` filter**; `clone3` keeps the default profile's `ENOSYS`, and `keyctl`/`mount` stay
  denied by the profile's `SCMP_ACT_ERRNO` default;
- persists `kernel.unprivileged_userns_clone=1` in `/etc/sysctl.d/90-charly-userns.conf` and applies it on
  a live venue where the sysctl exists;
- enables `containerd.service` and, on the Arch family, `buildkit.service`;
- **repairs the ownership of exactly the paths this layer owns**: `/var/lib/containerd`,
  `/run/containerd`, the blockfile snapshotter directory and its scratch image become `root:root` — the
  identity the packaged unit runs as. It deliberately does **not** `chown -R` the store: files inside a
  container rootfs must keep the ownership their container gave them. This narrow repair matters on a
  venue RE-DEPLOYED over the previous layer version, which ran `chown -R 1000:1000` and left those
  subdirectories uid-owned;
- gives the bed the **three-step shape** — **absence** (the distro's STOCK config, run as a private daemon
  on a private root/state/socket, serves no `krun`), **perform** (the member deploy runs the layer's own
  `run:` steps), **presence** (`crictl info` lists `crun` and `krun`, and the snapshotter the effective
  config declares — `overlayfs` — plus `native` and `blockfile` report `ok`) — with the config contract,
  the seccomp-profile contract, the ownership assertion and the user-namespace sysctl asserted beside it.

**One home for the assertions.** Every artifact and live assertion is in the BED's `plan:`, and nowhere
else. The candy's plan is the install timeline plus its one mandatory ADE `check:` (the daemon binary is
installed). That is forced by measurement, not preference: a cloud-image VM bed builds no image
(`bedBuildsImage` is false) and its member phase resolves no plan (`no plan steps resolved … this phase
asserted nothing`, `opencharly/plugin-check#110`), so a candy-plan check would run in no phase here.

The `xt_multiport` declaration (PR #6) and the `blockfile` snapshotter and its scratch image (PR #4) are
preserved. **One snapshotter choice is stated rather than implied:** CONTAINERD-IMAGES §1.1 carries no
snapshotter row, and CONTAINERD.md names `overlayfs` as the default (§1 rule 3, §3.3.2), so the CRI
declares `overlayfs`; `native`/`blockfile` remain served so the device-less and Firecracker paths survive.
The typed `containerd:` surface that makes the choice a declared value is still opencharly/spec#239.

**Two disclosures, stated rather than hidden.**

1. **The first bed attempt failed on the host, not on the change**: `vm-build` reported
   `ResourceExhausted: write … 0-disk.qcow2: no space left on device`; `df` showed `/` at 100 % (20 K
   available). RCA: the host's root filesystem was already full before the run, and no gate had a
   free-space precondition — the change was never reached. Root fix on the host: reclaimed regenerable
   caches (`go clean -cache`, 28 G; `journalctl --vacuum-size=500M`, 3.5 G), rebuilt the partial VM disk,
   re-ran. Every later run is green. This is an environment condition, not a product defect.
2. **The first version of the ownership check failed in the gate, for a real reason, and was
   fixed**: it ran `stat` as the deploy user, and `/var/lib/containerd` is mode 0700 root:root, so it
   could not traverse to the blockfile directory (`stat: cannot statx …: Permission denied`, run
   `2026.295.1915`). RCA: the check had been proven locally against a world-traversable temp path, not
   under the guest's real permissions. Root fix: read the four paths as root (`sudo -n`, the same helper
   the other probes use), re-proven under a 0700 root-owned store, and the green run above follows.
3. **The one deploy warning is the bed's fixture, not the layer**: each member deploy records
   `warning: linux: ignoring package upgrade (7.2.9.arch1-1 => 7.2.11.arch1-1)` — the base cloud image's
   kernel hold, which exists so the layer's `pacman -Syu` does not replace the RUNNING kernel's module
   tree mid-bed (the exact post-upgrade state `xt_multiport` refuses loudly on). The `check-live` and
