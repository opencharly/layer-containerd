# 2026.289.0839 — feat(containerd): serve the blockfile snapshotter, so a Firecracker pool can back a root drive

Agent: charly-dsh

## Summary

The layer rendered a `config.toml` whose CRI default was the `native` snapshotter and served nothing
else that can back a microVM **root drive**. The consumer that needs one — the Firecracker pool
substrate — refused to start, and had no configuration that would let it:

```
$ charly vm ssh check-fireactions-host 'journalctl -u charly-layer-fireactions-fireactions -n 12'
  containerd: snapshotter "devmapper" is not served by this containerd
$ sudo ctr plugins ls | grep snapshotter
  blockfile skip   devmapper skip   native ok   overlayfs ok        (containerd v2.4.2)
```

`opencharly/fireactions` (`server/config.go`) defines `SnapshotterDevmapper` as the compatibility
default and `SnapshotterBlockfile` as the file-backed snapshotter that "needs no LVM and no spare block
device, which makes a Firecracker pool possible on a host whose only storage is the root filesystem",
and `SnapshotterBacksRootDrive` accepts **only** those two — `native`/`overlayfs` are refused because a
directory mount cannot back a root drive. So on the previous image both acceptable values were `skip`
and **no valid configuration existed**.

Three changes, each derived from a measurement:

| change | the fact that required it |
|---|---|
| the daemon-preparation step creates and formats the scratch image the blockfile plugin **clones**, guarded so a re-run never re-`mkfs`es a file the running daemon is using. The size is a **named, env-overridable** value (`CHARLY_CONTAINERD_BLOCKFILE_SCRATCH_SIZE`, default `512M`) because it bounds how much snapshot data a pool can hold | `failed to generate scratch file: failed to copy scratch: failed to open source …/scratch_file: no such file or directory` |
| the rendered config gains `[plugins."io.containerd.snapshotter.v1.blockfile"]` (`root_path`, `scratch_file`, `fs_type`). **Additive** — the CRI default stays `native`, so existing consumers see no change | `blockfile` was `skip`; the stanza alone moved it to `error` |
| `e2fsprogs` is **declared** in the distro packages, because the step now needs `mkfs.ext4` | `mkfs.ext4` was previously assumed present rather than declared |

**The superseded assertion is deleted, not supplemented.** The previous `containerd-config-written`
check grepped the rendered file for `snapshotter = "native"` — the CRI plugin's default, which is not
the set the daemon serves. It **passed while `blockfile` was `skip` and the consumer could not start**,
so it could not fail for the property this change adds. It is removed; the assertion now exists **once**,
in this repo's own bed `check-containerd-vm`, which asserts the **daemon-reported** plugin set
(`native … ok` **and** `blockfile … ok`), and is where this repo asserts the substrate.
